# Scenario `threads`

Uses the driver from several threads at the same time, with Lua Lanes. Each lane is a Lua state of its own, in a thread of its own, with its own environment and connection; LuaSQL objects cannot be passed between lanes. The scenario checks what only real threads can show: calls of the driver and its client library from several threads at once, one thread blocked in a call while others go on, and the release of everything a lane left open when its Lua state ends.

With Oracle, the driver must create its OCI (Oracle Call Interface) environment with `OCI_THREADED`; otherwise the first case crashes the child process. A lane opens its connection itself from the environment variables (`laneconn.lua`); the scenario passes only the DBMS name and the module paths to it. The tasks of the lanes are in `scenarios/threadsLane.lua`.

The scenario is skipped without Lua Lanes, without `conn:prepare` or without the threads table of the backend. Cases that count or kill sessions need the admin connection and are skipped without it. A lane that hangs inside a call after a failed case is freed by killing its session; Lanes itself cannot cancel a lane inside a driver call.

## Cases

Each case runs once. *N* is the number of lanes: smoke 2, standard 4, nightly 8.

| Test               | Checks                                                                                                                                                                                                              | Results                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parallelQueries`  | N lanes run queries through `conn:execute` at the same time (smoke 50, standard 200, nightly 1000 queries per lane).                                                                                                | Pass: every lane returns the right sum and row count, and every value is an integer. Fail: a wrong sum, a float, an error or a crash.                                                                          |
| `parallelPrepared` | The same with prepared statements and parameters, plus a cursor with temporary CLOBs (Character Large Objects) every tenth query. Before they close, the lanes wait while their temporary LOBs are counted.          | Pass: sums, rows and CLOB lengths are right and no temporary LOB stays in an open session. Fail: anything else.                                                                                               |
| `parallelConnect`  | N lanes connect, query and close in a loop at the same time (smoke 5, standard 20, nightly 50 rounds per lane).                                                                                                     | Pass: every lane does all rounds and the sessions are back at the start afterwards. Fail: an error, a crash, or sessions left. Needs the admin connection.                                                     |
| `lockWait`         | Lane A locks a row; lane B waits for it with `FOR UPDATE WAIT 30`; lane C runs queries meanwhile; then A commits.                                                                                                   | Pass: C finishes while B is still blocked by A, and B then gets the row with A's value. Fail: C waits for B (a blocked call stops other threads), B ends early, or B gets a wrong value.                       |
| `deadlock`         | Lanes 1 and 2 each update one row, then each the other's row; lane 1 waits first, then lane 2 closes the circle.                                                                                                    | Pass: lane 1 gets `ORA-00060` (deadlock), its session works on and still sees its first update; lane 2 waits until lane 1 rolls back, then finishes; both rows hold lane 2's value. Fail: no deadlock error, the victim loses its first update or its locks too early, or a lane hangs. |
| `killDuringCall`   | A lane sleeps 20 seconds in a server call; the admin connection kills its session while it sleeps.                                                                                                                  | Pass: the call returns with a lost connection error (`ORA-00028`, `ORA-03113`) within 10 seconds, the next call fails too, close works, the session is gone. A kill answered with `ORA-00031` (marked for kill) counts as a kill. Fail: the call returns normally, takes too long, or the session stays. Needs the admin connection. |
| `laneErrorCleanup` | A lane raises an error with a connection, a statement and a cursor open.                                                                                                                                             | Pass: when the Lua state of the lane ends, the session is gone within 15 seconds. Fail: the session stays, or a crash. Needs the admin connection.                                                             |
| `laneEndCleanup`   | A lane ends normally with a connection and a cursor open.                                                                                                                                                            | As above.                                                                                                                                                                                                       |
| `envNotSendable`   | Sends an environment through a linda (the message queue of Lanes).                                                                                                                                                   | Pass: Lanes rejects it cleanly and the environment works on. Fail: it is sent, or a crash.                                                                                                                     |

## Phases

Iterations per phase: smoke 20, standard 200, nightly 1000; the first 300 iterations are warm-up (see [How Leaks Are Found](../README.md#how-leaks-are-found)), so the memory is measured only in tier nightly; sessions and server counters are checked in every tier. Extra counter: sessions of the test user.

| Phase      | Each iteration                                                                                                          | Fails when                                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `laneLoop` | each of N lanes, which live for the whole phase, connects, runs 5 queries and closes                                    | a sum is wrong, a lane fails or misses an iteration, or sessions, a counter or the memory grow (see [Phases](../README.md#phases)) |

The lanes of `laneLoop` live for the whole phase on purpose: threads that are started and ended in every iteration raise the memory of the process in steps that hide any leak. Starting and ending threads is checked by the cases, through the sessions.
