# Scenario `threads`

Uses the driver from several threads at the same time, with Lua Lanes. Each lane is a Lua state of its own, in a thread of its own, with its own environment and connection; LuaSQL objects cannot be passed between lanes. The scenario checks what only real threads can show: calls of the driver and its client library from several threads at once, one thread blocked in a call while others go on, and the release of everything a lane left open when its Lua state ends.

A lane opens its connection itself from the environment variables (`laneconn.lua`); the scenario passes only the DBMS name and the module paths to it. The tasks of the lanes are in `scenarios/threadsLane.lua`.

The scenario is skipped without Lua Lanes or without the queries of the backend (`offsetQuery`, `multiRowQuery`; with the bind API also `offsetBindQuery` and `clobRowsQuery`). Without the bind API (`conn:prepare` and `luasql.type`, e.g. `luasql.ado`) `parallelPrepared` is skipped and `laneErrorCleanup` leaves no statement open; every other case and the phase run; `parallelWriters`, `lockWait` and `deadlock` are skipped without the threads table, each case without the backend keys it needs. Cases that count or kill sessions need the admin connection and are skipped without it. A lane that hangs inside a call after a failed case is freed by killing its session; Lanes itself cannot cancel a lane inside a driver call.

## Cases

Each case runs once. *N* is the number of lanes: smoke 2, standard 4, nightly 8.

| Test               | Checks                                                                                                                                                                                                              | Results                                                                                                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `parallelQueries`  | N lanes run queries through `conn:execute` at the same time (smoke 50, standard 200, nightly 1000 queries per lane).                                                                                                | Pass: every lane returns the right sum and row count, and every value is an integer. Fail: a wrong sum, a float, an error or a crash.                                                                          |
| `parallelPrepared` | The same with prepared statements and parameters, plus a cursor with temporary CLOBs (Character Large Objects) every tenth query. Before they close, the lanes wait while their temporary LOBs are counted.          | Pass: sums, rows and CLOB lengths are right and no temporary LOB stays in an open session. Fail: anything else. Skipped without the bind API.                                                                 |
| `parallelConnect`  | N lanes connect, query and close in a loop at the same time (smoke 5, standard 20, nightly 50 rounds per lane).                                                                                                     | Pass: every lane does all rounds and the sessions are back at the start afterwards. Fail: an error, a crash, or sessions left. Needs the admin connection.                                                     |
| `parallelWriters`  | N lanes raise the value of the same row by one at the same time, each in transactions that begin with the update; every second transaction is rolled back (smoke 20, standard 100, nightly 250 transactions per lane). The lanes wait for the lock of the row, or with `backend.threadsLockSetup` for that of the database. | Pass: no lane fails, and the value is the number of commits. Fail: an error (e.g. a lock wait that ends with an error), a crash, or another value (a rollback that did not undo, a lost update). |
| `lockWait`         | Lane A locks a row; lane B waits for it with `FOR UPDATE WAIT 30`; lane C runs queries meanwhile; then A commits.                                                                                                   | Pass: C finishes while B is still blocked by A, and B then gets the row with A's value. Fail: C waits for B (a blocked call stops other threads), B ends early, or B gets a wrong value.                       |
| `deadlock`         | Lanes 1 and 2 each update one row, then each the other's row; lane 1 waits first, then lane 2 closes the circle.                                                                                                    | Pass: lane 1 gets `ORA-00060` (deadlock), its session works on and still sees its first update; lane 2 waits until lane 1 rolls back, then finishes; both rows hold lane 2's value. Fail: no deadlock error, the victim loses its first update or its locks too early, or a lane hangs. |
| `killDuringCall`   | A lane sleeps 20 seconds in a server call; the admin connection kills its session while it sleeps.                                                                                                                  | Pass: the call returns with a lost connection error (`ORA-00028`, `ORA-03113`) within 10 seconds, the next call fails too, close works, the session is gone. A kill answered with `ORA-00031` (marked for kill) counts as a kill. Fail: the call returns normally, takes too long, or the session stays. Needs the admin connection. |
| `laneErrorCleanup` | A lane raises an error with a connection, a statement and a cursor open (without the bind API: a connection and a cursor).                                                                                          | Pass: when the Lua state of the lane ends, the session is gone within 15 seconds (SQLite: no lock left on the file). Fail: the session stays, or a crash. Needs the admin connection.                         |
| `laneEndCleanup`   | A lane ends normally with a connection and a cursor open.                                                                                                                                                            | As above.                                                                                                                                                                                                       |
| `envNotSendable`   | Sends an environment through a linda (the message queue of Lanes).                                                                                                                                                   | Pass: Lanes rejects it cleanly and the environment works on. Fail: it is sent (the environment must work on all the same), or a crash.                                                                         |

## Phases

Iterations per phase: smoke 20, standard 200, nightly 1000; the first 300 iterations are warm-up (see [How Leaks Are Found](../README.md#how-leaks-are-found)), so the memory is measured only in tier nightly; sessions and server counters are checked in every tier. Extra counter: sessions of the test user.

| Phase      | Each iteration                                                                                                          | Fails when                                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `laneLoop` | each of N lanes, which live for the whole phase, connects, runs 5 queries and closes                                    | a sum is wrong, a lane fails or misses an iteration, or sessions, a counter or the memory grow (see [Phases](../README.md#phases)) |

The lanes of `laneLoop` live for the whole phase on purpose: threads that are started and ended in every iteration raise the memory of the process in steps that hide any leak. Starting and ending threads is checked by the cases, through the sessions.

## Oracle

The driver must create its OCI (Oracle Call Interface) environment with `OCI_THREADED`; otherwise the first case crashes the child process. In `parallelWriters` an `UPDATE` of the locked row waits until the holder commits or rolls back (Oracle has no lock timeout for DML).

## SQLite

There are no sessions: what a lane leaves behind is counted as the lock of other connections on the database file (`backend.leftoverCounter`, read by the probe of the admin connection, see SQLite under [DBMS-Specific Notes](../README.md#dbms-specific-notes)); it must be back at 0. In `lockWait` both lanes set a busy timeout first (`backend.threadsLockSetup`), and B waits for the write lock of the database instead of a row; so do the lanes of `parallelWriters`, one writer at a time. Their transactions begin with the update: a transaction that has read before it writes would get `database is locked` at once instead of waiting. `deadlock` is skipped: a second writer gets `database is locked` at once, SQLite does not wait in a deadlock. `killDuringCall` is skipped: there is no session to kill.

## DuckDB

There are no sessions: what a lane leaves behind is counted as connections to the database (`backend.leftoverCounter`, `duckdb_connection_count()`); they must be back where they were. Two transactions that change the same row conflict instead of waiting (see [`concurrency`](concurrency.md)), so `parallelWriters` raises the value of row 1 by inserting a row with id 1, and the value of a row is the number of its rows: the case checks parallel write transactions that do not conflict. `lockWait` and `deadlock` are skipped: DuckDB never waits for a lock. `killDuringCall` is skipped: there is no session to kill.

## Firebird

The lanes lock a row with `UPDATE` or `SELECT ... WITH LOCK` and wait without a limit (the default of Firebird). With `SNAPSHOT`, the isolation of `luasql.firebird` in a transaction, a transaction that waited for a lock cannot change or lock the row once the holder has committed: it gets `update conflicts with concurrent update`, and goes on only if the holder rolls back. `parallelWriters` and `lockWait` are therefore a limit when they fail with this error (`backend.threadsLimits`); any other error fails them. `deadlock` runs: Firebird detects the deadlock and gives one of the two lanes an error with `deadlock`; the other one goes on after the victim has rolled back. Firebird has no query for the attachment that blocks another one, so the cases wait a second for the block instead.

`killDuringCall` lets the lane run an `EXECUTE BLOCK` that loops for 20 seconds on the server (Firebird has no sleep), until `CAST('NOW' AS TIMESTAMP)` is 20 seconds later; the lane counts as busy while a statement of its attachment is active (`MON$STATE = 1` in `MON$STATEMENTS`). The kill is a `DELETE FROM MON$ATTACHMENTS`.

## PostgreSQL

The lanes lock a row with `UPDATE` or `SELECT ... FOR UPDATE`; the wait for a lock is limited with `SET lock_timeout`. With `READ COMMITTED`, the isolation of PostgreSQL, a transaction that waited for a row lock goes on once the holder has committed: `parallelWriters` and `lockWait` pass. The session that blocks another one is found with `pg_blocking_pids()`. `deadlock` gives a limit: PostgreSQL detects the deadlock after `deadlock_timeout` (1 second by default) and gives `deadlock detected` to the session that waited first; the error aborts its transaction, so its first update is no longer readable and every further statement fails with `current transaction is aborted` until the rollback (`backend.threadsLimits`).

`killDuringCall` lets the lane run `pg_sleep` on the server; the lane counts as busy while its session waits in it (`wait_event = 'PgSleep'` in `pg_stat_activity`). The kill is `pg_terminate_backend` on the admin connection; the lane gets `terminating connection due to administrator command`.

## MariaDB

The table is `luastress_threads` (InnoDB). The lanes lock a row with `UPDATE` or with `SELECT ... FOR UPDATE WAIT n`; an `UPDATE` waits up to `innodb_lock_wait_timeout` (50 seconds by default). The session that blocks another one is found in `information_schema.INNODB_LOCK_WAITS` with `INNODB_TRX`, on the admin connection; both come from a cache that InnoDB renews at most every 0.1 seconds, and the scenario waits for the blocking session in a loop.

`deadlock` gives a limit (`backend.threadsLimits`): InnoDB gives `Deadlock found when trying to get lock; try restarting transaction` (1213) to one session and rolls back its whole transaction, which frees its locks, so the other session gets its row at once. The victim does not keep its first update, and `luasql.mysql` returns `false` and a message from its `commit()` (the transaction was rolled back by an earlier error).

`killDuringCall` lets the lane run `SELECT SLEEP(n)` on the server; the lane counts as busy while its session shows the state `User sleep` in `PROCESSLIST`. The kill is `KILL CONNECTION` on the admin connection; the lane gets `Lost connection to server during query` (2013), the next call `Server has gone away` (2006).

## ODBC

The tables, locks and queries are those of the native backends; the lanes open their own connections through the DSN of the target. With `odbc_postgres`, `deadlock` passes without a limit: PostgreSQL gives `deadlock detected` to the session that waited first, and psqlODBC rolls back its statement to a savepoint of its own, so the transaction of the victim goes on with its first update and its locks; with `luasql.postgres` the error aborts the transaction. With `odbc_mariadb`, `deadlock` is a limit as with `luasql.mysql` (`backend.threadsLimits`): InnoDB rolls back the whole transaction of the victim, which frees its locks, so the other session gets its row at once; `luasql.odbc` cannot report it, the commit of the victim returns `true`. `killDuringCall` runs as with the native backends.

With `odbc_mariadb` the process memory of `laneLoop` is a limit (`backend.memoryLimits`): each of the 8 lanes connects once per iteration, and Connector/C loses about 250 bytes per TLS connect (MariaDB JIRA CONC-883, see [`connectionLifecycle`](connectionLifecycle.md#odbc)). In nightly of 23 November 2026 the trend after the warm-up was +1388 KB over 700 iterations, second round +1443 KB, about 250 bytes per connect; without TLS (`FORCETLS` off, 24 November 2026) it was +0 KB.

## ADO

Since task stress-ado-literal the scenario runs for `ado_postgres` and `ado_mariadb`, without `parallelPrepared` (`luasql.ado` has no bind API, decision of 25 November 2026). The tables, locks and queries are those of the ODBC backends, used through `conn:execute`. Every lane requires `luasql.ado`, and so luacom, in its own body (`laneconn.lua`), not through the `required` list or `on_state_create` of Lanes: luacom initializes COM for the thread that requires it. `laneErrorCleanup` leaves a connection and a cursor open, no statement.

Each lane connects without session pooling (`OLE DB Services=-2`, see [`cursorLifecycle`](cursorLifecycle.md#ado)), so the sessions of the lanes come and go as with ODBC. ADO cancels a command after `Connection.CommandTimeout`, 30 seconds by default; no wait of the scenario comes near it unless a case hangs: the lock waits of `parallelWriters`, `lockWait` and `deadlock` last a moment, and the sleep of `killDuringCall` (20 seconds) is killed as soon as it has begun.

The phase `laneLoop` uses a pool of N lanes made once, before the warm-up: the about 10 KB of private bytes per lane that requires luacom (luacom `ca4d26a`, measured in task core-ado; see the ADO topic of the manual, [`doc/ldoc/manual/10-ado.md`](../../doc/ldoc/manual/10-ado.md)) come before the measurement.

Results (smoke and nightly of 25 November 2026): every case except the two below passes with both targets, `killDuringCall` included. `laneLoop` keeps the sessions (2 -> 2) and the memory: in the nightly, 1000 iterations with 8 lanes, private bytes -3676 KB with `ado_postgres` and -7424 KB with `ado_mariadb`, without a trend. So no comparison with an older luacom was needed.

- `envNotSendable` is a limit with both targets (`backend.threadsLimits`, decided on 25 November 2026): `luasql.ado` is written in Lua, its environment is a table, and a linda copies it instead of refusing it. The copy shares no state with the original: it keeps the count of connections it had when it was sent, so with a connection open then its `close()` fails for good; a lane that requires luacom in its body cannot receive it (`'luacom' not found in main destination transfer database`). Lanes refuses connections and cursors at the send, as with the drivers written in C. The case checks that the original environment works on before it fails (probe `adoprobe-stress4.lua`, 25 November 2026; section Threads of the ADO topic of the manual).
- `deadlock`: with `ado_postgres` it passes, as with `odbc_postgres`: psqlODBC rolls back the statement of the victim to its own savepoint, and the victim keeps its first update and its locks. With `ado_mariadb` it is a limit, as with `odbc_mariadb` (`backend.threadsLimits`): InnoDB rolls back the whole transaction of the victim, which frees its locks, so the other session gets its row at once. `luasql.ado` cannot report it: after the error `@@in_transaction` of the victim is 0, and its `commit()` returns `true` (same probe).
